# Переход на Event-Driven архитектуру

## Проблемы и риски

1. Ответ `ins-product-aggregator` зависит от всех страховых компаний. Медленный или недоступный API задерживает весь запрос.
2. После подключения ещё пяти компаний число внешних вызовов удвоится. Вырастут время ожидания, объём ответов и число ошибок.
3. `core-app` обновляет каталог раз в 15 минут, а `ins-comp-settlement` — раз в сутки. Из-за этого сервисы используют разные версии тарифов.
4. Ежедневная выгрузка полисов из `core-app` создаёт пик нагрузки. При сбое выгрузки взаиморасчёты задерживаются, а повторная обработка может привести к дублям.

## Решение

Сервисы передают изменения продуктов и полисов через Kafka.

| Топик | Отправитель | Получатели | Данные |
| --- | --- | --- | --- |
| `product-updates` | `ins-product-aggregator` | `core-app`, `ins-comp-settlement` | Изменения продуктов и тарифов |
| `policy-events` | `core-app` | `ins-comp-settlement` | Оформленные полисы и изменения их статуса |

Агрегатор сам опрашивает каждую страховую компанию раз в 15 минут. Запросы выполняются независимо, с таймаутами и ограниченным числом повторов. При ошибке сохраняется последний успешный результат. Каталог хранится в собственной схеме PostgreSQL, изменения отправляются в Kafka.

`core-app` и `ins-comp-settlement` обновляют свои локальные каталоги из событий. Они используют разные группы потребителей Kafka, чтобы оба сервиса получали все изменения. Реплики одного сервиса делят обработку внутри своей группы.

После оформления полиса `core-app` отправляет событие с условиями страховки, включая тариф и сумму. `ins-comp-settlement` сохраняет эти данные и формирует реестры в своей БД. Передача реестров страховым компаниям остаётся ежемесячной. Ежедневный запрос полисов в `core-app` больше не нужен.

## Transactional Outbox

Таблицы outbox находятся в `core-app` и `ins-product-aggregator`. Сервис одной транзакцией сохраняет бизнес-данные и событие в таблицу `outbox`. Фоновый обработчик отправляет событие в Kafka и отмечает его отправленным после подтверждения брокера. При сбое отправка повторяется.

Получатель сохраняет данные и `event_id` одной транзакцией, затем подтверждает обработку сообщения. Уже обработанные события пропускаются. Для продуктов ключ сообщения — ID компании + ID продукта, для полисов — ID полиса. Версия объекта позволяет не применять устаревшие изменения.

Обновление через события происходит с задержкой, поэтому нужно следить за очередью outbox и отставанием потребителей. Для взаиморасчётов используются условия оформленного полиса, а не текущий тариф из каталога.
